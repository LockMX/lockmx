# 002. Internationalization (PT-PT and EN)

- Status: in progress
- Idea: `../ideas/project-brief.md`
- Decisions: `../decisions/0008-i18n-native-next.md`, `../decisions/0001-monorepo-single-web-app.md`, `../decisions/0004-unit-test-runner.md`

## Objective

Give the site two languages, PT-PT and EN, and nothing else, so that every later page is written once and translated through dictionaries. After this spec: every route lives under a locale prefix (`/pt/...`, `/en/...`), a first-time visitor is sent to the right locale, text comes from typed dictionaries, a language switcher exists, and lint fails if a hardcoded visible string is added to JSX.

Owner decisions (2026-10-04): native Next.js pattern with no i18n library, locale always in the URL path, first-visit locale from `Accept-Language` with PT as fallback, no cookie, infrastructure plus switcher plus tests as scope.

## Out of scope

- Real landing page content and copy (own spec). The home page here is a minimal placeholder.
- SEO beyond the basics: `hreflang` alternates, sitemap, localized metadata for every page. Only `<html lang>` and a translated title and description are included.
- Remembering the visitor's choice in a cookie (depends on the open cookie consent decision).
- Localized URL paths (`/pt/produtos` against `/en/products`): paths are the same in both locales.
- Formatting helpers for prices and dates (they arrive with the shop spec, using `Intl`).
- Email templates in PT-PT and EN (ADR 0005, own spec).
- A translation management tool or workflow.
- End-to-end tests.

## Tasks

### T1. Locale configuration and negotiation
- Description: add the locale configuration (supported locales `pt` and `en`, default `pt`, the `Locale` type, `isLocale`, and the value of `<html lang>` for each locale: `pt-PT` and `en`) and `resolveLocale(acceptLanguage)`, which returns the best supported locale for an `Accept-Language` header value, or the default. Install the two production dependencies after confirming their documentation.
- Planned files: `apps/web/src/lib/i18n/config.ts`, `apps/web/src/lib/i18n/negotiate.ts`, their tests, `apps/web/package.json`, `pnpm-lock.yaml`.
- Acceptance criteria: `pt-PT` and `pt-BR` give `pt`; `en-GB` gives `en`; an unsupported language (`fr`), a missing header, `*` and a malformed header give `pt`; quality values are respected (`en;q=0.9,pt;q=0.5` gives `en`). `resolveLocale` never throws.
- Tests: the cases above, written first.
- Commit: `feat: add locale configuration and negotiation`

### T2. Typed dictionaries
- Description: one dictionary module per locale with the minimal messages this spec needs (placeholder page title and description, home heading and text, the language switcher label), the `Messages` type, and a server-side `getMessages(locale)` that returns the dictionary of a given locale. Reading the current locale from the root parameter (`next/root-params`) is added in T3, because the `[lang]` segment it needs does not exist before. The PT dictionary defines the shape; EN must match it, enforced by the compiler.
- Planned files: `apps/web/src/server/i18n/messages/pt.ts`, `apps/web/src/server/i18n/messages/en.ts`, `apps/web/src/server/i18n/messages.ts`, a test.
- Acceptance criteria: removing a key from one locale fails `pnpm typecheck`. A test asserts that both locales have exactly the same keys and no empty values.
- Tests: the key parity and non-empty test, written first.
- Commit: `feat: add typed dictionaries`

### T3. Locale routing
- Description: add `src/proxy.ts` that redirects a request without a locale prefix to `/<locale>/<same path>` using `resolveLocale`, replaces a first segment that looks like a locale code but is not supported (for example `/fr` or `/fr/a`) with the resolved locale (`/pt` or `/pt/a` when there is no match), and leaves requests that already have a valid prefix alone; its matcher excludes `api`, `_next` and asset files. Move the root layout to `app/[lang]/layout.tsx` (`<html lang>` from the config, fonts and global styles kept, `generateStaticParams` for both locales, title and description from the dictionary). Replace the default page with a minimal translated page at `app/[lang]/page.tsx`. An unknown `lang` value that reaches the page still returns 404 (defense in depth).
- Planned files: `apps/web/src/proxy.ts`, `apps/web/src/app/[lang]/layout.tsx`, `apps/web/src/app/[lang]/page.tsx`, removal of `apps/web/src/app/layout.tsx` and `page.tsx`, a proxy test.
- Acceptance criteria: verified against a production build (`pnpm build`, then `pnpm start`): `/` with `Accept-Language: en` redirects to `/en`, with `pt-PT` to `/pt`, with no header to `/pt`; `/en` returns 200 with `<html lang="en">`; `/pt` returns 200 with `<html lang="pt-PT">`; `/fr` redirects to `/pt` and `/fr/a` to `/pt/a`; `/produtos` redirects to `/pt/produtos`; `/favicon.ico` is not redirected. Lint, typecheck, tests and build pass.
- Tests: unit tests for the proxy function (redirect and pass-through cases) written first. Pages are async Server Components, so they are covered by the manual build verification above and later by end-to-end tests.
- Commit: `feat: add locale routing`

## Boundaries

- Always: tests before code in each task; confirm Next.js behavior in the bundled docs; keep the proxy small (it will also host later checks).
- Ask first: adding any dependency not listed here; adding locales; changing URL structure.
- Never: hardcode visible text in components; store the locale in a cookie in this spec; add a top-level route whose name looks like a locale code (two or three letters), because the proxy treats it as an unsupported locale.

## Decisions taken at approval (2026-10-04)

1. URL segments are `pt` and `en`; `<html lang>` is `pt-PT` for `pt`.
2. A first segment that is not a supported locale is never shown as an error: a locale-shaped one (`/fr`) is replaced by the resolved locale, and any other path gets the prefix. The resolved locale is the default (`pt`) unless `Accept-Language` matches another supported locale.
