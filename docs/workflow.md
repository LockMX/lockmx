# Development workflow

Execution rules for the whole team and for the agents (Claude Code and Codex). `AGENTS.md` summarizes them and points here.

## Principles

- Never assume. Every decision is based on the latest official documentation for the installed version and on the existing code.
- Less is more. No speculative code, no abstractions without real use.
- One task, one commit. The history must clearly show the work done.

## Task cycle

1. Read the task in the spec (`specs/`) and the linked decisions (`decisions/`). If anything is ambiguous, ask before implementing.
2. Consult the relevant official documentation for the installed version.
3. Write first the test that describes the requested behavior and confirm that it fails.
4. Implement the minimum for the test to pass, then clean up (refactor) without changing behavior.
5. Verify: lint, typecheck, tests and build, according to what the task affects. A command is only reported as passing if it was run.
6. Commit the task, with code and tests together.

Tests are part of each task and go in that task's commit. A task without tests (configuration, documentation) states the reason in the spec.

Commands available today, from the root: `pnpm dev`, `pnpm build`, `pnpm lint`. The test and typecheck commands arrive with the technical foundation spec and are recorded here at that point.

## Commits

Format: `<type>: <message>`

| Type | When |
|---|---|
| `feat` | New functionality. |
| `arch` | Structure, configuration, tooling and dependencies. |
| `fix` | Bug fix. |
| `refactor` | Code change without changing behavior. |
| `docs` | Documentation. |

Rules:

- Short message, in English, imperative and lowercase (`arch: add drizzle configuration`).
- No mention of the model or agent that made the commit: no `Co-Authored-By`, no trailers, no "generated by".
- No icons, emojis or graphic symbols.
- One commit per task. Do not mix tasks or include unrelated changes.

## Branches and pull requests

A pull request (PR) is the request, made on GitHub, to merge a branch into `main`. It shows the changes, runs the automatic checks (CI) and only lets the code in once they pass.

- After the initial bootstrap steps, each spec has a branch: `feat/<NNN>-<subject>`, with the same identifier as the spec.
- `main` is always ready to ship. Nobody commits directly to `main` once CI is active.
- Merging into `main` uses "rebase and merge", to keep one commit per task in the history. Do not use "squash".
- Pushing, opening a PR and merging only happen on explicit request or authorization from the project owner.

Until CI and `main` protection exist, the bootstrap (cleanup, documentation, rules) is done directly on `main`.

## Actions that require explicit authorization

`push`, opening or merging a PR, deploy, production migrations, changes to external services (GitHub, hosting, database, payments, invoicing) and new production dependencies.
