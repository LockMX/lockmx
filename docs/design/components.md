# Components

The inventory of `apps/web/src/components/ui/`. Each component task of spec 003 adds its rows here; a component that is not listed does not exist yet.

## Rules

- **Text comes from the page.** Every visible string and every accessible name (`alt`, `aria-label`, `title`) is a prop. A component holds no Portuguese or English text and never reads a dictionary: the page calls `getMessages()` and passes strings down (`../architecture.md`, Internationalization).
- **Server Component by default.** `"use client"` only where the component holds state or effects.
- **Native elements first.** A link is an `<a>`, an action is a `<button>`, a choice is a real input. Nothing else is clickable.
- **Props** extend the native element's props, so `aria-*`, `name`, `form` and `ref` work. `className` is for layout (size, margin, placement). `style` is not accepted.
- **Tests** are written first and sit next to the component.
- **Imports.** Code outside `components/ui/` imports from `@/components/ui` (`index.ts`), never from the file of a component.
- **Classes** are joined with `classNames` (`components/ui/class-names.ts`). There is no class merging: a `className` from the caller must not repeat a property the component already sets (size, colour, display).

## Notes per component

- **Icon.** Adding an icon is one import and one line in the map in `core/icon.tsx`. An icon never has a name of its own: the control around it does (ADR 0010).
- **Button.** Navigation uses `ButtonLink`, so it is an anchor; `Button` is only for actions. While `loading` the native `disabled` attribute is set, which is what keeps the button a Server Component; the page changes the label if it wants the wait announced in words. `variant="outline-inverse"` and the `ghost-inverse` icon button belong on an inverse surface.
- **Slanted button.** The background is a clipped pseudo-element, not the button itself, so the focus outline is not cut. It has no visible border, so the outline variants are not meant to be slanted.
- **IconButton.** With a `count` above zero the accessible name is the label followed by the number ("Carrinho 3"), and the number is not read a second time. The ring around the count takes the colour of the surface the variant is made for (`ghost-inverse`: the inverse surface).
- **Badge.** Always has text. `dot` and colour are additions to it.
- **Field.** `Input`, `Textarea` and `Select` use it themselves; use it directly only around another control. A label is required. An error is shown with an icon and text inside a polite live region that is always present, so an error that appears later is announced; the hint stays visible next to it. The required mark is hidden from assistive technology, which gets the native `required` attribute instead, and `requiredLabel` is its tooltip.
- **Input, Textarea, Select.** The native control has no border of its own: the box around it draws focus, invalid and disabled from the state of the control (`forms/control-styles.ts`). Invalid adds a second line to the border, so it does not depend on colour. `Select` is the native element, so the list, the keyboard and the mobile picker are the browser's.
- **Checkbox, Radio, Switch.** Each is the real native input, drawn by its own classes at its real size, so focus, the keyboard and form submission are the browser's and none of them is a Client Component. The state is never colour alone: a check mark, a dot, the position of the thumb. The name is the label only; the description (and the `aside` of a radio option) is linked with `aria-describedby`. `onChange` is the native change event, not the new value. They are made for light surfaces: their text is dark. They have no error text of their own yet.
- **Radio.** A `fieldset` with a `legend`; the shared `name` gives the arrow keys and the single tab stop. In the `card` variant the whole card is the label, and the selected card has a second line and a tint.
- **Switch.** A checkbox with `role="switch"`: the state comes from `checked`, and it submits with its form like a checkbox (present when on, absent when off).
- **QuantityStepper.** The field takes digits only. What is typed is a draft: `onChange` fires when the draft is a number in range, and leaving the field clamps it (an empty field goes back to the last value), so a value outside `[min, max]` is never emitted. Up and Down arrows change the value by one. At a limit the button keeps the focus and is `aria-disabled`. A polite live region announces the value after a button press, not while typing. While the draft is out of range the field is `aria-invalid`. A Server Component page cannot pass `onChange`: it uses the stepper uncontrolled, with `name`, inside a form. The `name` goes on a hidden input that holds the settled value, and Enter settles the draft before the form submits, so the form never receives a draft, an empty string or a number out of range. The server validates the quantity again all the same. `onChange` fires on each valid keystroke (typing 12 emits 1, then 12): a caller that sends each change to the server must debounce. It has no visible label; the name comes from `label`.
- **SearchBar.** A `role="search"` form whose field is a combobox with a listbox (APG, list autocomplete with manual selection). The focus never leaves the field: Down and Up move an active option (`aria-activedescendant`) and wrap, Enter takes the active option and does not submit, Enter with none submits, Escape closes the list and keeps the text, leaving the field closes it. Choosing a suggestion puts its label in the field and calls `onSelect`; it does not submit. The bar shows the suggestions whose label contains the text, without regard to case or accents, six at most; the parent supplies the candidates and the bar fetches nothing. A parent that already filtered on something other than the label will see rows dropped. A polite live region announces the number of suggestions or `noResultsLabel`; no empty list is shown. The texts are plain data so a Server Component page can pass them: `resultsLabel.one` is used for a count of 1 and `other` for the rest, which is right for Portuguese and English only. Without `onSubmit` the form submits natively under `name`, so a page can use it with `action` and no script of its own. The field has no visible label; the name comes from `label`, never from the placeholder. Limitation: the list is positioned under the field and is not in the top layer, so do not put a `SearchBar` with suggestions inside a container that scrolls or clips, such as the body of a `Dialog`. There the list is cut off, the container gains a scrollbar, and a press on that scrollbar takes the focus from the field and closes the list.
- **Card.** A static card is a `div` (or the element in `as`) and never reacts to the pointer. With `href` the whole card is one `next/link` anchor, and with `onClick` one `button`; nothing else makes a card clickable. The content of an interactive card is its accessible name, so it holds no other control, and a button card holds no block elements (HTML allows only phrasing content in a `button`). A card with a title, an image and its own button is built the way `ProductCard` is (spec 003, T10), not with an interactive `Card`. The lift on hover is skipped under reduced motion. A static `inverse` card sets `data-surface="inverse"`, so the controls inside it get the yellow focus ring; an interactive one does not, because its own ring is drawn outside it, on the page.
- **Tabs.** The APG tabs pattern with automatic activation: Left and Right move the focus and select, wrapping at the ends; Home and End go to the first and last tab; Up and Down are left to the page. Only the selected tab is in the tab order, and Tab goes from it to the panel, which is focusable. Every panel is rendered and the ones not selected are `hidden`, so `aria-controls` always points at something and the content can come from a Server Component page. The selected tab is not marked by colour alone: the underline variant draws a slanted bar in the text colour (a yellow bar is under 3:1 on a light surface), the segmented variant a boundary in `--border-control`. A tab with a `count` is named "label count".
- **Tooltip.** Wraps one focusable element and gives it `aria-describedby` with `cloneElement`, keeping a description it already has. The tooltip is always in the page (`hidden` when not shown), so the description reaches assistive technology whether it is visible or not. It shows on hover and on focus and stays while either lasts, including while the pointer is over the tooltip itself (the gap is padding of the tooltip); Escape dismisses it wherever the focus is, until the next hover or focus (WCAG 1.4.13). It holds text only and never takes the focus. It is not a place for information the user needs: a touch screen has no hover. It is at most `max-w-60` wide and centred on its trigger, so a trigger at the edge of a narrow screen can push it out; place such a trigger away from the edge. An `IconButton` already shows its `label` as a native `title`: wrapping one in a `Tooltip` with the same text would say it twice.
- **Toast and Toaster.** A toast is a `status`, or an `alert` for the `danger` tone, on a black surface (`data-surface="inverse"`). The tone has its own icon shape as well as its colour, and the words are the caller's. It holds no state: the caller renders it and removes it in `onClose`. It stays until closed unless `duration` is given. A toast with a `duration` shows a yellow bar along its bottom edge that fills over that time, so it is seen to be about to close; the bar is animated with the Web Animations API, because its length is a prop, and is hidden from assistive technology. A toast never closes itself in under five seconds, the time waits while the pointer is over it or the focus is inside it and starts again after, and a toast with an `action` cannot have a `duration` (a type error). `Toaster` is the fixed region, bottom right, that toasts are rendered into. Only the toasts in it take the pointer. Closing a toast with its button removes the focused element, so the caller decides where the focus goes next. It must be rendered once with the page, empty: it is the live region (`aria-live="polite"`), and a live region announces only what is added after it exists. There is no toast store or hook yet; the first feature that needs one adds it.
- **Dialog.** A modal on the native `<dialog>`, opened with `showModal()`, so the top layer, the inert page behind it and the focus trap are the browser's. Controlled: `open` decides, and `onClose` is called for the close button, Escape, a click on the backdrop and anything else that closes the element (a form with `method="dialog"`); the caller answers by setting `open` to false, and until then the dialog stays. So it needs a Client Component parent. It is named by its `title` (an `h2`) and described by `description` when there is one; keep the description to one sentence, since longer or structured text belongs in the body. Its content is rendered only while it is open, so a form in it starts fresh each time. On opening, the browser puts the focus on the first focusable element, which is the close button; an `autoFocus` on a field inside does not change that (React focuses on mount, before the dialog is shown, and writes no `autofocus` attribute). On closing, the focus goes back to the element that had it before, if it is still in the page. The body scrolls when the content is taller than the viewport; the title, the close button and the footer stay in view. The page behind does not scroll (`html:has(dialog:modal)` in `globals.css`). A press that starts inside and ends on the backdrop, as when selecting text, does not close it. A toast shown while a dialog is open sits behind the backdrop, cannot be reached and is not announced: the `Toaster` is not in the top layer, and the inert page is out of the accessibility tree. A `Tooltip` open inside a dialog does not stop Escape, so one press closes both.
